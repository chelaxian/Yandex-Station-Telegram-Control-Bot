# Развёртывание и откат

Примеры ниже — шаблоны для хоста бота, не установщик на колонку. Версия3.0.0a2 установлена в личный Linux LXC владельца по его прямому запросу с отдельным release/venv, приватной миграцией конфигурации, сохранением прежнего кода и проверенным автоматическим откатом. Это испытательная alpha, не квалифицированный production-релиз.

## Рекомендуемый первый запуск

1. Подготовьте отдельный bot token и личный тестовый чат. Не запускайте два poller с одним токеном.
2. Установите нужный commit LUNA отдельно по актуальному руководству конкретной модели. Сначала проверяйте read-only `GET /api/device`. Не меняйте rootfs, OTA и ограничения сети ради установки этого бота.
3. Организуйте локальный SSH tunnel: например, `ssh -N -L 127.0.0.1:18146:127.0.0.1:8100 <existing-station-alias>`. Используйте уже проверенный alias/ключ. Не отключайте проверку host key. Пример не создаёт bootstrap или автозапуск LUNA.
4. Скопируйте `config.example.toml` в приватный `config.toml`. Сверьте canonical `expected_model` с живым ответом. Не используйте retail name или старое имя платформы вместо canonical model.
5. Передайте `TELEGRAM_BOT_TOKEN` через секреты окружения и выполните `doctor` → `run`.
6. В личном чате проверьте `/menu`, `/stations`, `/status`, `/capabilities`. Затем по отдельности испытайте разрешённые операции на целевых моделях, с видимым/слышимым подтверждением.

## systemd на отдельном Linux-хосте

`deploy/stationbot.service` — шаблон: пользователь `stationbot`, код и venv в `/opt/stationbot`, config и environment file в `/etc/stationbot`, `state_dir="/var/lib/stationbot"`. Каталог секретов и файлы должны быть доступны только владельцу процесса/администратору. Unit не устанавливает SSH tunnel и LUNA. Подготовьте их отдельными уже проверенными службами; работоспособность после reboot требует отдельного теста.

Остановка: `systemctl stop stationbot`. Бот корректно завершает polling, освобождает HTTP sessions и БД. Нельзя считать флаг `enabled` или запущенный PID доказательством работающего Telegram UI.

Если SSH сервера станции запрещает TCP forwarding, не меняйте его конфигурацию вслепую. Для уже авторизованных ADB-устройств можно использовать локальный `adb forward` к порту LUNA. `deploy/adb_luna_forward.py` поддерживает конкретный serial и одну port mapping, не сбрасывает другие mappings и не пересоздаёт исправную mapping посреди записи. ADB server следует запускать отдельной службой на loopback, а не привязывать его lifetime к первой колонке. Связь app→forward→server оформляйте через `Wants`/`After`, чтобы отказ транспорта не останавливал Telegram-интерфейс. Helpers восстанавливают mappings после возврата server; они проверяют его доступность перед вызовом ADB client, чтобы не запускать конкурирующий daemon. В испытанном Debian29.0.6 синтаксис foreground server — `adb -L tcp:5037 server nodaemon`; фактический bind127.0.0.1 проверен. Хосту не требуется Windows-ПК. Это транспорт, не установщик или boot supervisor LUNA на самой колонке.

## Docker

Образ содержит только новый `src/stationbot`, не legacy, ADB и звуковые материалы. Монтируйте конфигурацию read-only и отдельный writable volume state для UID10001. Передайте token через секреты окружения. Пример `127.0.0.1` внутри контейнера относится к самому контейнеру; существующие Windows/host forwards из него не доступны автоматически. Подготовьте локальный tunnel внутри доверенной сети контейнера или собственный TLS proxy с проверкой Bearer. Не публикуйте LUNA admin port в WAN.

## Откат

Остановите новый процесс и вернитесь к предыдущему проверенному deployment. Новый runtime не переносит старые config.ini/Telethon session, не прошивает устройства, не меняет OTA и автозапуск. Для воспроизведения исходной кодовой базы используйте ветку `alfa`; это не рекомендация запускать небезопасные legacy installers.

Перед обновлением скопируйте закрытую SQLite БД вместе с конфигурацией в приватное место. Держите старый wheel и соответствующие зависимости. База с более новой schema version отклоняется старым runtime; downgrade миграции не выполняются автоматически. Аудиозаписей в БД нет.

## Критерии production-готовности

Не выполнены в этой alpha: полная feature parity 2.7; квалификация каждой модели; реальные Telegram E2E с отдельным токеном; двусторонний голос/VoIP; квалифицированные playback/TTS/camera/maintenance providers; station-local distribution и boot persistence; нагрузочные/длительные испытания и проверка обновления/отката deployment. Публикация репозитория и зелёный unit CI не закрывают эти критерии.
